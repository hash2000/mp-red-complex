# Хранилища и миграции

Хранилища описываются в `bootstrap.yaml` в разделе `stores.items`. Имя хранилища
совпадает с именем, передаваемым в `DatabasesService::connection()`.
Отсутствующее в конфигурации хранилище тоже можно открыть: по умолчанию оно
размещается в `data/<имя>.db` внутри профиля, без шифрования, с интервалом
проверки WAL 60000 мс и максимальным размером 20 МБ.

У хранилища можно задать `path` (относительно каталога профиля или абсолютный),
`encrypted`, `wal.checkInterval`, `wal.maxSizeMb` и список `migrations`:

```yaml
stores:
  items:
    example:
      path: data/example.db
      encrypted: false
      migrations:
        - version: 20251113181900
          description: Initialize database
          up: stores/migrations/example/20251113181900-up-Initialize-database.sql
          down: stores/migrations/example/20251113181900-down.sql
```

Пути SQL-файлов разрешаются относительно каталога `bootstrap.yaml`. Версия —
дата и время в формате `yyyyMMddHHmmss`; имена файлов обязаны содержать ту же
версию и направление. Описание после `-up` необязательно. Указываются оба
файла, а миграции применяются по возрастанию версии, независимо от порядка в
YAML. Файлы, не перечисленные в конфигурации, не загружаются.

Ранее зарегистрированные в коде миграции и их версии больше не поддерживаются.
Рабочая копия конфигурации в профиле должна содержать перечисленные SQL-файлы.

## Резервные копии

Копии файлов баз создаёт документ «Резервное копирование баз данных»
(`database-backup`, модуль `DatabaseModule`). Копии лежат в профиле:

```text
backups/<имя хранилища>/<yyyyMMdd-HHmmss-zzz>.db
```

Копируется файл базы как есть (для `encrypted: true` — зашифрованный файл).
Перед копированием WAL сворачивается, поэтому снимок состоятелен; перед
восстановлением создаётся страховочная копия `*-before-restore.db`. Подробнее —
`docs/database-backup/README.md`.
