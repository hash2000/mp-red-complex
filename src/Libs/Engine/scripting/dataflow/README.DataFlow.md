# Спецификация DataFlow DSL v1.0

## 1. Общие принципы и философия

Данный документ описывает декларативный язык (DSL) для определения графов обработки данных (Dataflow Graphs).

**Ключевые архитектурные решения:**
1.  **Единственный источник истины (Single Source of Truth):** Поведение процессора (чистый вычислитель, побочный эффект, требовательность к потоку выполнения) определяется исключительно его **нативным реестром типов**, а не атрибутами в YAML-файле.
2.  **Строгая топология связей:** Данные передаются только через явные связи (`inputs`) внутри узлов. Глобальных списков ребер нет.
3.  **Явный контроль запуска:** Выполнение начинается строго с узлов, перечисленных в `entrypoints`. Никакие другие узлы не могут инициировать выполнение самостоятельно.
4.  **Композируемость:** Любой файл DataFlow может использоваться как отдельный процессор внутри другого графа. Для этого он должен объявить свой интерфейс (`params` и `outputs`).
5.  **Разделение данных и эффектов:** Секция `outputs` предназначена только для возврата данных родителю. Побочные эффекты (запись в UI, файлы, сеть) выполняются нативно и не требуют явного объявления в выходных портах графа, если они не возвращают данные.

## 2. Структура документа YAML

Базовая структура файла:

```yaml
version: "1.0"                # Версия схемы для обратной совместимости
name: <unique_identifier>     # Имя графа/процессора
description: <text>           # Человекочитаемое описание

# Интерфейс процессаора (если этот файл используется как graph:<type>)
interface:
  params:                     # Входные параметры извне
    <param_name>:
      type: <string|int|bool|...>
      default: <value>        # Опционально
      required: true/false    # По умолчанию false, если есть default
  
  outputs:                    # Выходные данные для родителя
    <output_name>: <node_id>.<port_name>

# Настройки исполнения всего графа
execution:
  mode: oneshot | periodic | service | event
  timeout_ms: <int>           # Общий таймаут выполнения (опционально)
  error_policy: abort | continue | retry

# Точки входа. Список ID узлов, которые инициируют запуск.
entrypoints:
  - <node_id>
  - <node_id>

# Описание всех узлов графа
nodes:
  <node_id>:
    type: <processor_type>    # Тип из реестра или "graph:<sub_graph_name>"
    
    # Статические параметры конфигурации узла
    params:
      <key>: <value>          # Может содержать шаблоны $interface.params.xxx
    
    # Динамические входы данных (связи)
    inputs:
      <input_port_name>: <source_node_id>.<source_port_name>
      
    # Политика выполнения конкретного узла (переопределяет defaults реестра)
    policy:
      executor: gui | pool | dedicated
      batch_size: <int>
      queue_size: <int>
      backpressure: block | drop_oldest | drop_newest | error
      priority: low | normal | high
      retry_limit: <int>
```

## 3. Детальное описание секций

### 3.1. Version, Name, Description
*   **Version**: Строка вида `"MAJOR.MINOR"`. Используется парсером для выбора логики валидации.
*   **Name**: Уникальный идентификатор графа. Если граф вызывается как `graph:name`, этот параметр является ключом поиска.
*   **Description**: Произвольный текст для документации.

### 3.2. Interface
Определяет контракт данного DataFlow при использовании его как компонента более высокого уровня.

*   **Params**: Переменные, которые внешний граф передает внутрь текущего. Доступны внутри `nodes.*.params` через шаблон `$interface.params.<name>`.
*   **Outputs**: Порты данных, которые текущий граф возвращает внешнему миру. Формат ссылки: `<internal_node_id>.<port_name>`.
    *   *Примечание:* Эффектные узлы (WriteEffect) не обязаны быть включены в `outputs`, если их задача — только изменение внешнего мира без возврата данных.

### 3.3. Execution
Глобальные настройки жизненного цикла графа.

*   **Mode**:
    *   `oneshot`: Граф выполняется один раз до завершения всех активных веток. Используется для старта приложения, загрузки конфигов.
    *   `periodic`: Граф перезапускается по расписанию (требует дополнительных полей `schedule`).
    *   `service`: Постоянно работающий граф, реагирующий на события или входящие соединения.
    *   `event`: Запуск по триггеру (внешнее событие).
*   **Error Policy**: Что делать, если узел падает.
    *   `abort`: Остановить весь граф немедленно.
    *   `continue`: Пропустить ошибку, продолжить выполнение независимых веток.
    *   `retry`: Попытаться перезапустить упавший узел согласно его политике.

### 3.4. Entrypoints
Список ID узлов, которые являются точками старта.

*   Узел в списке `entrypoints` **не обязан** иметь пустой список `inputs`. Он может ждать данных от других entrypoints или внешних источников, но сам факт наличия в этом списке означает, что движок рассматривает его как потенциальный инициатор цепочки.
*   **Правило строгости:** Если узел имеет обязательные входы (по реестру), но они не подключены ни к какому источнику, и узел не указан в `entrypoints` (или указан, но не получает данных), это ошибка валидации ("Deadlock" или "Missing Input").
*   Обычно `entrypoints` содержат узлы-источники (Sources), у которых нет входных портов данных.

### 3.5. Nodes
Карта всех исполняемых единиц.

#### Type
Идентификатор типа процессора.
*   Нативный тип: `"FileReader"`, `"PaletteBuilder"`.
*   Вложенный граф: `"graph:palette.builder"`. Префикс `graph:` указывает парсеру рекурсивно загрузить другой YAML-файл.

#### Params
Статические настройки. Значения могут быть литералами или ссылками на интерфейс:
```yaml
params:
  path: $interface.params.source_file
  threshold: 0.8
```

#### Inputs
Маппинг входных портов узла на выходные порты других узлов.
Формат: `<target_port>: <source_node>.<source_port>`
Пример:
```yaml
inputs:
  text: read_file.raw_content
  config: parse_json.settings
```
*   Ключи должны соответствовать именам входных портов, определенным в реестре для данного `type`.
*   Ссылки должны указывать на существующие узлы и их существующие выходные порты.

#### Policy
Локальные переопределения поведения. Если не заданы, используются дефолты из реестра процессоров.
*   `executor`: Куда отправить задачу. `gui` (главный поток), `pool` (пул рабочих потоков), `dedicated` (выделенный поток).
*   `batch_size`: Сколько элементов накапливать перед вызовом `process()`.
*   `backpressure`: Стратегия при переполнении очереди входящих данных.

## 4. Семантика ролей узлов (Вычисляемые свойства)

Роли узлов не пишутся в YAML явно. Они выводятся движком на основе Реестра Процессоров и структуры графа.

| Роль | Определение | Источник истины |
| :--- | :--- | :--- |
| **Source** | Узел, у которого нет обязательных входных портов данных. | Реестр (Purity == ReadEffect / None) + Структура (пустой `inputs`) |
| **Processor** | Узел, преобразующий данные. Имеет входы и выходы. | Реестр (Purity == Pure) |
| **Sink (Data)** | Узел, чей выход указан в глобальном `outputs` графа. | Секция `outputs` |
| **Effect** | Узел, изменяющий внешний мир (UI, FS, Net). | Реестр (Purity == WriteEffect) |
| **Entrypoint** | Узел, инициирующий выполнение. | Секция `entrypoints` |

### Правило оптимизации (Pruning)
При компиляции графа применяется следующее правило удаления неиспользуемых веток:
1.  Если узел является **Pure Processor** и его выход не используется нигде (ни в `inputs` других узлов, ни в `outputs` графа), такой узел удаляется из плана исполнения.
2.  Если узел является **Effect** (WriteEffect), он **никогда не удаляется**, даже если его выход никто не читает. Его наличие в графе подразумевает необходимость выполнения побочного действия при получении входных данных.

## 5. Правила разрешения неоднозначностей и валидации

Для обеспечения детерминированности применяются следующие жесткие правила:

1.  **Запрет неявных связей.** Нельзя предполагать связь между соседними узлами. Все связи должны быть явно прописаны в `inputs`.
2.  **Запрет дублирования связей.** Один входной порт одного узла может быть связан только с одним выходным портом другого узла (или константой, если поддерживается реестром). Мультиплексирование должно происходить внутри процессора.
3.  **Циклические зависимости.** По умолчанию запрещены. DAG (Directed Acyclic Graph) обязателен. Исключение: явные feedback-петли, разрешенные только для специализированных stateful-процессоров через специальный синтаксис (например, `recurrent: true` в policy), который меняет семантику ожидания данных.
4.  **Недостижимые узлы.** Узел, который не является `entrypoint`, не имеет входящих связей и не является целью какой-либо связи, считается ошибкой конфигурации (Orphan Node).
5.  **Типизация портов.** При компиляции проверяется совместимость типов данных (`dtype`) выходного порта источника и входного порта приемника. Несовпадение типов — ошибка сборки.
6.  **Шаблонизация переменных.** Синтаксис `$path.to.var` разрешается строго иерархически:
    *   `$interface.params.x` -> Параметры вызывающего контекста.
    *   `$globals.y` -> Глобальные константы графа (если секция `globals` добавлена).
    *   Отсутствие переменной — ошибка времени компиляции (Compile-time Error), если она статически анализируема, иначе Runtime Error.

## 6. Жизненный цикл исполнения

Процесс обработки DataFlow состоит из следующих этапов:

1.  **Loading & Parsing:**
    *   Чтение YAML файла.
    *   Построение AST (Abstract Syntax Tree).
2.  **Resolution:**
    *   Разрешение вложенных графов (`graph:type`). Рекурсивная загрузка зависимостей.
    *   Подстановка значений `$interface.params` из вызывающего контекста.
3.  **Validation:**
    *   Проверка существования всех `type` в Реестре Процессоров.
    *   Проверка корректности `inputs` (существуют ли указанные порты?).
    *   Проверка типов данных портов.
    *   Поиск циклов (Topological Sort attempt).
    *   Проверка достижимости всех `entrypoints`.
4.  **Compilation:**
    *   Построение `CompiledGraph`: карта узлов, список рёбер, метаданные (is_effect, is_pure, thread_affinity).
    *   Применение правил Pruning (удаление неиспользуемых Pure-узлов).
    *   Генерация плана исполнения (Execution Plan).
5.  **Instantiation:**
    *   Создание экземпляров нативных C++ объектов процессоров.
    *   Вызов метода `configure(params)` для каждого узла.
    *   Создание каналов связи (queues/buffers) между портами согласно политикам `batching/backpressure`.
6.  **Execution:**
    *   Инициализация планировщика.
    *   Триггеринг узлов из списка `entrypoints`.
    *   Event Loop:
        *   Узел производит данные -> Отправка в канал выхода.
        *   Канал доставки данных в вход следующего узла.
        *   Следующий узел проверяет готовность (все ли обязательные входы получены?).
        *   Если готов -> Постановка задачи в Executor (GUI/Pool).
7.  **Finalization:**
    *   Сборка результатов в `outputs` (если граф используется как компонент).
    *   Гарантированное завершение всех Effect-узлов (ожидание их колбеков).
    *   Освобождение ресурсов.
    *   Возврат статуса успеха/ошибки.

## 7. Пример использования

### Файл `palette.builder.yaml` (Чистый процессор)

```yaml
version: "1.0"
name: palette.builder
description: "Builds QPalette from YAML spec without applying it"

interface:
  params:
    theme_path: 
      type: string
      required: true
  outputs:
    palette: build_palette.palette

execution:
  mode: oneshot

entrypoints:
  - read_spec

nodes:
  read_spec:
    type: FileReader
    params:
      path: $interface.params.theme_path

  parse_spec:
    type: YamlParser
    inputs:
      text: read_spec.text

  build_palette:
    type: PaletteBuilder
    inputs:
      spec: parse_spec.value
```

### Файл `startup.dark.theme.yaml` (Граф с эффектом)

```yaml
version: "1.0"
name: startup.dark.theme
description: "Loads dark theme and applies it to UI"

interface:
  params:
    theme_path:
      type: string
      default: "assets/themes/dark.yaml"

execution:
  mode: oneshot
  error_policy: abort

entrypoints:
  - load_theme_data

nodes:
  # Используем предыдущий граф как процессор
  load_theme_data:
    type: graph:palette.builder
    params:
      theme_path: $interface.params.theme_path

  # Эффектный узел. Не входит в outputs, но будет выполнен обязательно.
  apply_to_ui:
    type: StateWriter  # Реестр знает: GUI Thread, WriteEffect
    inputs:
      value: load_theme_data.palette
    params:
      target: app.application
    policy:
      executor: gui
```
