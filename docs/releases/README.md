# Релизы: тег, сборка, архив

Документ описывает, как в проекте устроена публикация версий: что запускает
сборку, где появляется архив и что делать, если релиз не собрался.

## Коротко

GitHub сам по себе не следит за тегами: тег — это просто метка в истории.
Сборку запускает **workflow** — файл `.github/workflows/release.yml` в
репозитории. В нём объявлено:

```yaml
on:
  push:
    tags:
      - 'v[0-9]*'
```

Когда вы пушите тег вида `v0.1.0`, GitHub запускает этот workflow на
`windows-latest`. Он собирает `Launcher` в конфигурации Release, упаковывает
переносимый zip и создаёт **GitHub Release**, прикладывая zip к релизу.

Архив появляется не «внутри тега», а в разделе **Releases** (вкладка на главной
странице репозитория) и на странице `/releases/tag/v0.1.0` — релиз и тег связаны
между собой. В списке тегов (`/tags`) виден сам тег, а скачать файлы можно из
релиза.

## Что происходит после `git push origin v0.1.0`

1. GitHub находит в запушенном коммите `.github/workflows/release.yml` и видит,
   что тег подходит под фильтр `v[0-9]*`.
2. Запускается прогон во вкладке **Actions → Release**.
3. Workflow ставит CMake 4.1+, окружение Visual Studio (MSVC), компилятор
   clang-cl и Ninja, затем зависимости через vcpkg (триплет
   `x64-windows-release`, только Release-библиотеки).
4. `cmake --build build --target Launcher` собирает приложение.
5. `scripts/package-release.ps1` собирает каталог развёртывания: `Launcher.exe`,
   библиотеки Qt и зависимости, плагины Qt, `src/Configurations`, `LICENSE`,
   `README.txt`, `RedComplex.cmd`, `version.txt`, — и упаковывает его в
   `RedComplex-<версия>-win64.zip`.
6. Zip прикладывается к прогону как artifact (его можно скачать из лога) и,
   если это пуш тега, загружается в GitHub Release.

Версия берётся из имени тега: `v0.1.0` → `0.1.0` → `RedComplex-0.1.0-win64.zip`.
Если в версии есть дефис (`v0.2.0-beta`), релиз помечается как pre-release.

## Один раз перед первым релизом

1. **Workflow должен быть в репозитории.** GitHub запускает workflow из того
   коммита, на который указывает тег. Поэтому `.github/workflows/release.yml`
   должен быть закоммичен и влит в ветку, с которой вы ставите тег (обычно
   `main`). Если поставить тег на коммит без этого файла, ничего не запустится.
2. **Actions должны быть включены** в репозитории (Settings → Actions →
   General → Actions permissions).
3. **Права на создание релиза.** В workflow указано
   `permissions: contents: write`. Если в настройках репозитория выбран режим
   «Read repository contents permission», шаг создания релиза упадёт с ошибкой
   403. Тогда в Settings → Actions → General → Workflow permissions нужно
   выбрать «Read and write permissions».
4. **Первый прогон долгий.** vcpkg собирает Qt 6 и остальные зависимости из
   исходников — это может занять десятки минут. Пакеты кэшируются
   (`actions/cache` + бинарный кэш vcpkg), поэтому повторные сборки версий идут
   несколько минут. При изменении `vcpkg.json` кэш пакетов пересобирается.

Никаких personal access token и секретов заводить не нужно: workflow
использует автоматический `GITHUB_TOKEN`.

## Как выпустить версию

Из корня репозитория:

```powershell
git switch main
git pull

# Аннотированный тег: в нём хранится автор, дата и сообщение.
git tag -a v0.1.0 -m "RedComplex 0.1.0"

# Пуш именно тега, а не ветки.
git push origin v0.1.0
```

То же самое можно сделать через веб-интерфейс: **Releases → Draft a new
release → Choose a tag → создать тег `v0.1.0` → Publish release**. Надёжнее
всё-таки пушить тег из консоли: на push тега GitHub реагирует гарантированно.
Если тег создан только через UI и прогон не появился, отправьте его вручную:

```powershell
git fetch --tags
git push origin v0.1.0
```

Теги не переиспользуются. Если нужно пересобрать версию, удалите тег и
поставьте заново:

```powershell
git tag -d v0.1.0                 # локально
git push origin :refs/tags/v0.1.0 # удалить на GitHub
```

Если прогон по тегу упал из-за ошибки в самом workflow, перезапуск
(**Re-run all jobs**) не поможет: он использует тот же коммит и тот же файл.
Порядок такой:

1. Исправить workflow и запушить в `main`.
2. Проверить сборку через **Run workflow** — ручной запуск берёт workflow из
   выбранной ветки.
3. Удалить тег (см. выше) и поставить его заново на новый коммит.

## Как проверить сборку, не выпуская версию

У workflow есть ручной запуск: **Actions → Release → Run workflow**, поле
`version` (например, `0.1.0-test`). В этом режиме собирается только artifact
прогона — тег и релиз не создаются. Скачать его: внизу страницы прогона,
раздел **Artifacts**.

Кнопка «Run workflow» появляется только тогда, когда workflow уже есть в
ветке по умолчанию (`main`).

## Что внутри архива

```text
RedComplex-0.1.0-win64/
  RedComplex.cmd        запускалка: копирует конфигурацию в профиль при первом запуске
  Launcher.exe
  Qt6*.dll, *.dll       Qt 6, OpenSSL, SQLCipher, libsodium, yaml-cpp, ICU
  platforms\, tls\,     плагины Qt: платформа Windows, стили, HTTPS,
  styles\, ...          форматы изображений и т. д.
  Configurations\       эталонная конфигурация (bootstrap.yaml, applications,
                        assets, stores, dataflow)
  README.txt            инструкция для пользователя
  LICENSE
  version.txt
```

Часть зависимостей Qt лежит в vcpkg не в `bin`, а в `tools` (например,
`brotlidec.dll` и `bz2.dll`, которые нужны `freetype.dll` и `Qt6Network.dll`).
Скрипт упаковки добирает DLL и оттуда, а в CI дополнительно проверяет через
`dumpbin`, что каждая импортируемая DLL есть в пакете или в System32
(флаг `-VerifyDependencies`) — такая ошибка ловится до публикации релиза.

## Первый запуск у пользователя

Приложение читает конфигурацию не рядом с `exe`, а из профиля:

```text
%LOCALAPPDATA%\Hash2000\red-complex
```

Поэтому архив нельзя просто распаковать и запустить `Launcher.exe` на чистой
машине: сначала нужна эталонная конфигурация в профиле. Это делает
`RedComplex.cmd`:

- если `%LOCALAPPDATA%\Hash2000\red-complex\bootstrap.yaml` нет — копирует туда
  папку `Configurations`;
- затем запускает `Launcher.exe`.

`RedComplex.cmd /update-config` повторно копирует эталонную конфигурацию поверх
рабочей (полезно после обновления сборки), не трогая `data` и `users` в профиле.

## Локальная проверка упаковки

Тот же скрипт, что использует CI, можно запустить локально:

```powershell
cmake --build build\x64-Clang-Debug --target Launcher
.\scripts\package-release.ps1 -Version 0.0.0-local -BuildDirectory build\x64-Clang-Debug -KeepStaging
```

С флагом `-VerifyDependencies` скрипт дополнительно проверяет через `dumpbin`,
что для всех DLL из пакета найдены их импортируемые библиотеки; в CI флаг
включён, локально для него нужно окружение Visual Studio (скрипт подхватит его
сам).

Скрипт создаёт `artifacts\RedComplex-0.0.0-local-win64.zip` и (с `-KeepStaging`)
оставляет распакованный каталог для проверки. Локально `windeployqt` может
недоступен или не работать в ограниченном окружении — скрипт в этом случае
предупреждает и копирует библиотеки и плагины Qt из vcpkg вручную. В CI
`windeployqt` работает и дополнительно приносит runtime компилятора MSVC.

## Ограничения и что стоит знать

- **Только Windows x64.** Для Linux/macOS нужен отдельный job с другим
  триплетом vcpkg; сейчас проект собирается и упаковывается под Windows.
- **Тесты в релизном workflow не запускаются.** Сборка релиза намеренно
  короткая; тесты удобнее держать в отдельном CI-workflow по push/PR.
- **Компилятор — clang-cl.** Проект штатно собирается им (см.
  `CMakeSettings.json`), поэтому CI воспроизводит эту конфигурацию: Visual
  Studio даёт заголовки и библиотеки, clang-cl — компилятор. Чтобы собирать
  MSVC, уберите `-DCMAKE_C_COMPILER` и `-DCMAKE_CXX_COMPILER` из шага
  «Конфигурация».
- **Версии портов vcpkg зафиксированы.** В `vcpkg.json` задан
  `builtin-baseline: 0df93a05b9de080129e653ec4776d7e14a1b2e4f` — это коммит
  vcpkg, с которым собран образ раннера `win25/20261116.335` (он был актуален
  23 ноября 2026 и дал рабочий релиз 0.1.0). CI ставит ровно те версии
  библиотек, что и этот образ, поэтому сборки не «перескакивают» на новые
  порты, а кэш пакетов остаётся рабочим. Версия baseline попадает в
  `version.txt` внутри архива. Сам исполняемый файл vcpkg по-прежнему берётся
  с образа раннера — на версии портов он не влияет, их задаёт baseline.
- **Приватные репозитории.** Минуты GitHub Actions для Windows-раннеров
  считаются с коэффициентом 2, а первая сборка Qt долгая. Кэш пакетов и кэш
  Actions заметно сокращают расход при следующих версиях.
- **Размер релиза.** Основной вес архива — ICU, Qt и плагины; это нормально
  для Qt-приложения. Если понадобится уменьшить, можно перейти на сборку Qt
  без ICU или исключить неиспользуемые модули.

### Обновление версий vcpkg

Версии меняются осознанно, иначе теряется смысл фиксации:

1. Взять коммит vcpkg из notes образа раннера: **actions/runner-images →
   Releases → Windows Server …**, строка `Vcpkg (build from commit …)`.
   Либо обновить локальный клон: `git -C <vcpkg> fetch` и
   `git -C <vcpkg> checkout <sha>`.
2. Заменить `builtin-baseline` в `vcpkg.json` на полный 40-символьный хеш.
3. Прогнать **Run workflow**: кэш пакетов пересобирается под новые порты —
   один раз и, возможно, долго (как первая сборка Qt).

Тот же baseline действует и локально. Перед первой сборкой после смены
коммита обновите клон vcpkg (`git -C <vcpkg> pull`), иначе vcpkg не сможет
прочитать порты из зафиксированного коммита. Порты, версии которых совпадают
с уже установленными, пересобираться не будут.

## Если релиз не собрался

| Симптом | Причина и что делать |
|---|---|
| Прогон вообще не появился | Тег поставлен на коммит без `.github/workflows/release.yml`, Actions выключены или имя тега не подходит под `v[0-9]*`. |
| Ошибка 403 на шаге «GitHub Release» | Нет права `contents: write` (см. «Один раз перед первым релизом»). |
| `Invalid triplet name … on expression: $env:VCPKG_TARGET_TRIPLET` | PowerShell не разворачивает `$env:` внутри аргумента, начинающегося с `-D`, и в CMake уходит буквальная строка. В workflow триплет подставляется выражением GitHub (`${{ env.… }}`); обновите файл до актуальной версии. |
| `CMake was unable to find a build program corresponding to "Ninja"` | На `windows-latest` Ninja не предустановлен. Шаг «Ninja» скачивает его (в крайнем случае ставит через Chocolatey) и добавляет в `PATH`. |
| Сборка падает на конфигурации | Проверьте лог шага «Конфигурация»: обычно это ошибка vcpkg или несовместимость версии CMake. |
| Релиз создан, но без файла | Смотрите шаг «Упаковка» и «Артефакт прогона»: скрипт не создал zip (ошибка в логе). |
| Пользователь запустил `Launcher.exe` и получил ошибку конфигурации | Нужно запускать `RedComplex.cmd`: он копирует `Configurations` в профиль. |
| «Не удаётся найти `brotlidec.dll` / `bz2.dll`» при запуске | В пакет не попали зависимости Qt, которые vcpkg держит в `tools\Qt6\bin`. Скрипт упаковки теперь берёт DLL и оттуда, а проверка `-VerifyDependencies` ловит такие пропуски в CI. |
| Не работают HTTPS-запросы | В архив не попал `tls\qopensslbackend.dll`; проверьте предупреждение шага упаковки. |

## Связанные файлы

- `.github/workflows/release.yml` — сам workflow.
- `scripts/package-release.ps1` — сборка каталога развёртывания и zip.
- `packaging/RedComplex.cmd`, `packaging/README.txt` — файлы, попадающие в архив.
- `vcpkg.json` — зависимости и features (Qt, SQLCipher, libsodium, yaml-cpp…).
