# Резервное копирование баз данных

Документ модуля `DatabaseModule` создаёт копии файлов баз, зарегистрированных в
контекстах `.store.<alias>`, и восстанавливает базу из копии. Реестр хранилищ —
тот же, что использует `DatabasesService`: `bootstrap.yaml` (`stores.items`)
содержит только перечисление имён, а настройки каждого хранилища лежат в
`stores/<alias>.yaml`; контексты создаёт `BootstrapContextBuilder`.

Основные классы:

- `DatabaseBackupService` — `src/Content/DatabaseModule/services/database_backup_service.h`;
- `DatabaseBackupWidget` — `src/Content/DatabaseModule/widgets/database_backup_widget.h`;
- `DatabaseBackupDocument` — `src/Content/DatabaseModule/documents/database_backup_document.h`;
- `DatabaseStoreInfo`, `DatabaseBackupInfo` — `src/Content/DatabaseModule/models/database_backup.h`.

## 1. Реестр хранилищ

Сервис перечисляет только **зарегистрированные** хранилища — живые контексты
`.store.<alias>`:

```text
.store
  accounts   path=<профиль>/data/accounts.db, encrypted=false, wal...
  game       path=<профиль>/data/game.db, encrypted=true
  ...
```

Для каждого хранилища `DatabaseBackupService::stores()` собирает:

| Поле | Источник |
|---|---|
| `alias` | имя контекста `.store.<alias>` |
| `path` | `DatabasesService::databasePath(alias)` (переменная `path` или `data/<alias>.db`) |
| `encrypted` | переменная `encrypted` контекста |
| `walCheckInterval`, `walMaxSizeMb` | переменные `wal.checkInterval`, `wal.maxSizeMb` (по умолчанию 60000 и 20) |
| `fileExists`, `fileSize` | файловая система |
| `backupCount`, `lastBackupAt` | каталог копий |

Хранилище, которого нет в контексте `.store`, для сервиса не существует — даже
если файл базы лежит в профиле.

## 2. Где лежат копии

```text
<path.profile>/backups/<alias>/<yyyyMMdd-HHmmss-zzz>.db
```

Имя сортируется по времени; при совпадении миллисекунд добавляется суффикс
`-1`, `-2` и т. д. Каталог копий конкретного хранилища возвращает
`backupDirectory(alias)`, список — `backups(alias)` (новые сверху).

Копия — **файл базы как есть**. Для хранилища с `encrypted: true` это
зашифрованный файл SQLCipher: копия не содержит открытого текста, а
восстановление не требует отдельного экспорта. Поэтому сервис не использует
`VACUUM INTO`/`sqlcipher_export` и не зависит от ключа при копировании файла.

## 3. Создание копии

`createBackup(alias)`:

1. открывает соединение через `DatabasesService::connection(alias)` — это
   гарантирует, что файл существует и миграции применены;
2. выполняет `PRAGMA wal_checkpoint(TRUNCATE)`. После этого WAL пуст, а
   основной файл содержит последний коммит: копия файла состоятельна;
3. копирует файл в каталог копий и сверяет размер;
4. отправляет `backupCreated(alias, path)` и `backupsChanged(alias)`.

Если база зашифрована, а ключ не установлен (`DatabasesService::setEncryptionKey`),
соединение не откроется и сервис вернёт ошибку — копию зашифрованной базы без
ключа сделать нельзя. Если файла базы ещё нет, открытие создаст его с
применёнными миграциями: копия будет содержать схему без пользовательских
данных.

## 4. Восстановление

`restoreBackup(alias, backupPath)`:

1. проверяет копию `DatabasesService::verifyDatabaseFile`: файл открывается с
   учётом шифрования хранилища и проходит `PRAGMA integrity_check`. Проверка
   идёт на отдельном соединении, рабочая база не затрагивается;
2. закрывает соединение с базой (`DatabasesService::closeDatabase`) — WAL
   сворачивается;
3. сохраняет текущий файл страховочной копией
   `<yyyyMMdd-HHmmss-zzz>-before-restore.db` в тот же каталог; если копию
   сохранить не удалось, восстановление не начинается;
4. удаляет `-wal`, `-shm`, `-journal` старой базы и заменяет файл копией;
5. открывает базу заново — применяются миграции, если копия старее схемы;
6. отправляет `backupRestored(alias, path)` и `backupsChanged(alias)`.

Если восстановленная база не открывается (например, копия сделана с другим
ключом), сервис возвращает страховочную копию на место и сообщает об ошибке —
база остаётся в прежнем состоянии.

Удаление (`removeBackup`) разрешено только для файлов внутри каталога копий
этого хранилища: чужие файлы сервис не трогает.

## 5. Документ и виджет

Тип документа: `Content.Database.DatabaseBackup`, xtype
`database-backup`, синглтон.

```text
documents action=create, target=database-backup
```

Документ открыт в боковой панели приложения `base`
(`applications/base/main.yaml`). Слева — хранилища (имя, количество копий,
🔒 для зашифрованных), справа — путь к файлу, настройки WAL, таблица копий и
действия:

| Действие | Что делает |
|---|---|
| «Создать копию» | `createBackup` для выбранного хранилища |
| «Восстановить» | подтверждение и `restoreBackup` для выбранной копии |
| «Удалить» | подтверждение и `removeBackup` |
| «Каталог» | открывает каталог копий хранилища |
| «Обновить» | перечитывает `.store` и каталог копий |

Выбранное хранилище документ хранит в переменной контекста `store`; по ней он
восстанавливает выбор после повторного открытия (метаданные типа описывают
переменную для диалога создания документа). Сведения о хранилище показываются
в панели «Свойства» (группа «Свойства документа»).

Ошибки виджет показывает в строке статуса, а документ дублирует их в консоль
через `CommandController::printError`. Диалоги используются только для
подтверждения восстановления и удаления.

## 6. Регистрация

- Сервис: `ServicesFactory::registerServices` (`src/Launcher/services.cpp`)
  — `registerFactory<DatabaseBackupService>`, зависимости `Resources`,
  глобальный контекст и `DatabasesService`.
- Тип документа: `WidgetsBuilder` (`src/Launcher/widgets_builder.cpp`),
  метаданные — `registerDocumentMetadata`.
- Оформление вкладки: `assets/themes/dark/documents.yaml`; стили —
  `assets/themes/dark/stylesheets/database-backup.qss`
  (подключён в `stylesheets/index.yaml`).

## 7. Тесты

`TestDatabaseBackup` (`src/Content/DatabaseModule/tests/test_database_backup.cpp`)
проверяет:

- список хранилищ из `.store` и путь по умолчанию;
- создание копии, содержимое копии и счётчик в `.store`;
- восстановление, замену данных и появление страховочной копии;
- сохранение шифрования (копия не начинается с заголовка SQLite) и отказ
  восстановления без ключа;
- отказ восстановления из повреждённого файла без изменения рабочей базы;
- удаление только внутри каталога копий;
- выбор хранилища виджетом и синхронизацию `store` в контексте документа.

## 8. Ограничения

- Операции выполняются в потоке вызывающей стороны (GUI). Для больших баз
  создание копии занимает время и блокирует интерфейс.
- Копия не сжимается и не упаковывается в архив — это файл базы.
- Страховочные копии не удаляются автоматически; чистить каталог можно вручную
  (файлы с суффиксом `-before-restore`).
- Копия зашифрованной базы привязана к ключу SQLCipher: восстановить её можно
  только с тем же ключом.
- После восстановления открытые документы других модулей могут показывать
  данные, загруженные до замены файла: переоткройте их или нажмите «Обновить».
